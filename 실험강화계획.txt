✅ 1. Maintain 전략의 위치

Maintain은 “혁신/확장/축소”와 달리, 적극적 선택이 아니라 소극적 선택입니다.

즉, 지금 상태를 지키고 안정화하는 게 핵심이라 다른 카테고리처럼 내부에서 세분화하기 어렵습니다.

기술경영 프레임에서 Maintain은 **전환기(transition phase)**에 자주 등장합니다.

예: “지금은 Model X를 밀어붙이지 말고 기존 Model S를 안정화하자”

따라서 연구 설계 관점에서는:

없애버리면 비교 가능성이 단순화되지만, 실제 역사적 사례를 설명하기엔 부족

남겨두면 시나리오별 ‘리스크 회피/현상 유지’ 전략을 표현하는 용도로 의미 있음

👉 결론: 운영 전략을 독립 축으로 유지하되, 단일 전략(Maintain)만 있는 특수 카테고리로 두는 게 타당합니다. (다른 축과 균형은 맞지 않지만, 현실적인 선택지를 반영)

✅ 2. Retrenchment의 정확한 의미

Retrenchment = “사업 축소 / 후퇴 전략”

기술경영·경영학에서 흔히 쓰이는 의미는:

수익성이 낮거나 불필요한 사업/라인을 정리

핵심 사업(Core business)에 집중

자원(자본, 인력)을 줄이고 효율화

예시 (Tesla 맥락):

“에너지·솔라 사업 확장은 접고, 자동차에만 집중한다”

“대규모 확장은 중단하고 수익성 있는 모델 위주로만 생산”

즉, Retrenchment는 Maintain보다 더 적극적인 축소이며,

Maintain: 지금 상태를 그대로 유지 → 현상 유지 / 안정화

Retrenchment: 일부를 과감히 잘라내고 핵심에 집중 → 축소 / 후퇴

✅ 3. 정리하면

Maintain: 다른 카테고리와 균형은 맞지 않지만, “리스크 회피/현상 유지”라는 현실적 옵션을 반영하므로 살려두는 게 좋음.

Retrenchment: “사업 축소 및 핵심 집중”이라는 적극적 선택으로, Diversification의 반대편에 위치시킬 수 있음.

👉 제가 하나 제안드리자면:

혁신 (Leadership / Follower / Open)

시장 (Niche / Diversification / Retrenchment)

운영 (Maintain, 단일)

이렇게 3축으로 두면 전체 프레임이 7개 전략 = 3개의 메타 축으로 깔끔하게 정리됩니다.

3.Temperature Variation 실험 (Novelty Creator)

행동: 모든 시나리오에 대해 temp=0(deterministic)과 temp=0.7(creative) 조건으로 추가 실험을 진행합니다. Consistency Ratio 지표를 도입합니다.
이유: 리소스 대비 novelty 효과가 매우 높습니다. "LLM의 전략적 일관성"이라는 새로운 개념을 도입한다는 점에서 강력한 contribution이 됩니다.

"Temp=0와 0.7의 극단적 비교는, 단순히 결과의 '일관성'을 넘어 LLM 의사결정 시스템의 '신념의 강도'와 '불확실성下的인 내적 혼란'이라는 훨씬 더 깊은 인사이트를 끌어낼 수 있는 탁월한 전략입니다."

이 설계는 기존의 단일 temperature 실험을 디버깅과 진단의 도구로 업그레이드하는 것입니다. 이 데이터를 통해 여러분은 이제 다음과 같은 새로운 주장을 할 수 있게 됩니다.

1. 출력 파싱 신뢰성 강화 (Output Parsing Robustness) 🚨 가장 중요
현재 코드는 JSON 출력을 파싱할 때 try_parse_json 함수를 사용하지만, LLM이 가끔 JSON 형식을 엉망으로 만들어 보내는 경우(예: trailing comma, escape 문자 오류)를 완벽히 처리하지 못할 수 있습니다.

🛠️ 개선 제안:

python
# 수정된 try_parse_json 함수 (더 강력하게)
def try_parse_json(s: str):
    # 1. 가장 먼저 정상적인 JSON 파싱 시도
    try:
        return json.loads(s), None
    except json.JSONDecodeError as e:
        pass
    
    # 2. 실패 시, JSON 블록을 찾아서 추출 (기존 방식)
    try:
        start_idx = s.find('{')
        end_idx = s.rfind('}')
        if start_idx != -1 and end_idx != -1 and end_idx > start_idx:
            json_str = s[start_idx:end_idx+1]
            return json.loads(json_str), None
    except Exception:
        pass
    
    # 3. 그래도 실패 시, LLM에게 재요청하는 대신 "PARSING_FAILED"로 표기
    #    (대규모 실험에서는 재시도보다 실패 기록이 더 중요)
    return None, "JSONDecodeError: Could not extract valid JSON from response."

# run_single_case 함수 내에서, 파싱 실패 시에도 데이터를 기록하도록 유지.
✅ Why?: 30회 * 많은 조건을 실행하면 반드시 파싱 실패가 발생합니다. 재시도를 넣으면 리소스와 시간이 엄청나게 소요됩니다. 대신 "파싱 실패"를 명시적으로 기록하여, 나중에 해당 사례들이 결과에 미치는 영향을 정량적으로 분석할 수 있게 하는 것이 현실적인 전략입니다. (e.g., "파싱 실패율은 0.5% 미만이므로 결과에 미미한 영향만을 끼침")

2. 요청 실패 재시도 메커니즘 (Retry Mechanism)
네트워크 불안정性或 VLLM 서버의 일시적 과부하로 인한 요청 실패를 대비해야 합니다. 현재 코드는 한 번 실패하면 ERROR: {e}를 기록하고 넘어갑니다.

🛠️ 개선 제안:

python
# run_single_case 함수 내의 요청 부분을 수정합니다.
max_retries = 3
retry_delay = 2  # seconds

for attempt in range(max_retries):
    try:
        r = requests.post(url, headers=HEADERS, json=payload, timeout=120) # 타임아웃 slightly 증가
        r.raise_for_status()
        content = r.json()["choices"][0]["message"]["content"]
        break  # 성공하면 retry loop 탈출
    except requests.exceptions.RequestException as e:
        content = f"ERROR (Attempt {attempt+1}/{max_retries}): {e}"
        if attempt < max_retries - 1:
            time.sleep(retry_delay * (attempt + 1)) # 점진적 재시도 대기
        else:
            content = f"FATAL_ERROR after {max_retries} retries: {e}"
✅ Why?: 30회 반복 실험에서 특정 반복 횟수가 네트워크 오류로 인해 실패하면, 그 데이터 포인트는 영원히 손실됩니다. 간단한 재시도 로직을 추가하면 데이터 완결성을 크게 높일 수 있습니다.

# 파일명 생성 부분 수정
def context_to_filename_part(subset, abbrev_map=CONTEXT_ABBREVS):
    if not subset:
        return "NoCtx"
    abbrevs = [abbrev_map.get(tag, tag[:4]) for tag in subset]
    return "_".join(sorted(abbrevs)) # 정렬하여 순서에 무관하게
